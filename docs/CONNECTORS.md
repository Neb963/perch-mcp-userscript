# OAuth Connectors

A Connector is the OAuth principal at the exact resource URL `https://<gateway>/mcp/<connectorId>`. The v2 Grant authorizes only Workspaces assigned to that Connector under current policy. Multiple conversations using one Connector share its authority. Isolate tasks with separate Connectors when necessary.

1. Pair once, then create a named Connector. Open the matching client authorization request and approve only its verified resource, client, scope, redirect and short code.
2. Explicitly assign each intended Workspace to the Connector. The Operator verifies the actual ready editor Generator ID, Draft ID and installation when attaching or rebinding. An empty default Draft ID is valid.
3. Install version-matched local knowledge in the agent client. Call `workspace_status({})` for assigned Workspaces and supply the intended Target to each execution. Report a missing/stale Target and obtain explicit intent for a replacement.
4. On normal idle/clean rebind, keep the Connector endpoint and v2 Grant. The old Target becomes stale and the browser obtains a new lease. Resolve Holds and acknowledge dirty or unknown old state before committing.
5. Use `operation_status` with the original Operation ID/key and Target when a response is lost. Never issue a new key to replay an uncertain effect.

Legacy v1 routes, approvals and Grants remain fixed to the original Workspace and Binding during staged rollout. Freeze targetless admission, settle old work, verify browser compatibility and complete fresh Connector-level OAuth consent before the atomic v2 authority switch. Refresh the client catalog after the switch. One-time reauthorization may be needed even with the existing endpoint URL. Do not copy an admin credential or token into connector configuration or put one in a URL. Exact rollout predicates are in [the v0.3 implementation specification](v0.3/PERCH-MCP-V0.3-IMPLEMENTATION-SPEC.md#25-compatibility-migration).

## Historical v1 Agent connectors and operational evidence

1. In the intended native editor, create a Workspace and select Attach current editor. Confirm Generator ID and Draft ID; an empty default Draft ID is valid. Workspace identity is not inferred from a Slug alone.
2. Create a named Agent for that Workspace. Copy its exact `https://<gateway>/mcp/<agentId>` URL. Each Agent has a separate protected resource audience. Do not add tokens to URLs.
3. Add a remote/custom MCP connector in the chosen AI web client. Use OAuth; there is no external OAuth application registration required per Agent. This implementation uses official OAuth server/resource handlers and dynamic client registration where supported.
4. Complete the client authorization redirect. The authorization page displays the Agent, Workspace, validated redirect, requested scope and matching short code. In Perch MCP → Agents, approve the exact request and code; never approve a different pending client.
5. Call `workspace_status`, `get_instructions`, `list_skills`, and `skill` before changing source. Retrieve the `generator-development` workflow. All knowledge is available through tools, including clients without Resource/Prompt interfaces.
6. Source and preview actions return durable operation handles. Poll `operation_status` to retrieve their terminal results. An MCP conversation/request ID is not a durable idempotency key. Do not repeat a mutation whose outcome is unknown.

MCP transport sessions do not identify a Workspace. The authenticated Grant, exact Agent endpoint and current binding do. A connector reused in several conversations shares its Grant and queue; it does not acquire conversation identity. Use one connector assignment per independent agent task.

Rebinding revokes old Grants and advances fencing. A pending authorization cannot silently follow a new binding or expanded permission policy. Reauthorize after changes. Revocation denies new dispatches and child permits; already consumed permits may have effects that must be reconciled.

The default policy includes source read/write, preview control and Resource reads. Preview JavaScript, computation, public fetch, Save, public upload, media and production state each require their own classes. Publish/delete/production replacement require operation-bound human approval as well. Resource text cannot grant permissions.

The pinned official SDK v2.4.0 serves the `2026-07-28` per-request profile and the `2025-11-25` / `2025-06-18` legacy profiles. These wire formats and mismatch rejection pass local Worker integration tests. Unsupported or mismatched protocol versions fail explicitly. Real ChatGPT, Claude and Gemini connector compatibility remains an external acceptance gate; their current account UI and plan availability were not verified.

No optional URL bearer-token mode is enabled. The OAuth client owns its access/refresh tokens; the manager never displays them. Do not paste a management credential into a connector.

## ChatGPT OAuth troubleshooting and verified rollout (v0.1.2)

The Cloudflare Worker **and** the Violentmonkey userscript must be updated. If Git-connected auto-deployment is enabled, verify it succeeded instead of creating a second Worker or destroying the existing KV namespace. Open `https://YOUR-WORKER.workers.dev/health` and confirm `version: "0.1.2"`. Install the matching v0.1.2 `perch-mcp.user.txt` using Violentmonkey and reload the Perchance editor. Existing pairing, Workspace bindings, and library contents remain unchanged.

Start a **new** ChatGPT OAuth authorization after upgrading; any five-minute code from the old build is expired. Keep Perch MCP → Agents open: pending authorizations poll automatically every four seconds. Verify the Agent, Workspace, client, callback and code before selecting `Approve exact request`, then return to ChatGPT's authorization page and choose `Continue after approval`. If Continue is pressed too early, the gateway provides a `Check approval again` button rather than losing the one-time authorization handle.

The gateway allows the exact ChatGPT web origin on the **public OAuth/MCP** protocol endpoints; it does not allow ChatGPT access to private `/api/v1/admin/` or `/api/v1/tab/` routes. Browser/OAuth clients must still complete PKCE, exact approval and bound Grant checks. No raw bearer secrets belong in URLs.

A Gateway error on a read-only GET may be retried automatically once; ambiguous management writes are never replayed. Distinct `GATEWAY_TIMEOUT` and `GATEWAY_UNAVAILABLE` diagnostics identify timeout versus connectivity/CORS/CSP failure. On failure, check the browser Console and the deployed Worker version before reauthorizing. The previous Cloudflare `OAUTH_KV` resource should be reused in upgrades—never delete it to fix a failed build.

## OAuth form Origin and diagnostics (v0.1.3)

**Root cause of the live `SCOPE_DENIED` at Continue:** the gateway HTML originally set `Referrer-Policy: no-referrer`, which causes browsers to send `Origin: null` on normal HTML form POSTs. The gateway then rejected `POST /authorize/complete`. Version 0.1.3 uses `Referrer-Policy: origin` for the OAuth form pages (only the gateway origin is sent, never the URL query or approval handle) and accepts a privacy-mode null Origin only for the exact POST completion route, with a non-cross-site Fetch Metadata condition and the existing one-time 256-bit handle, server-side approval, expiry, PKCE S256, exact client, and binding verification. Explicit foreign-origin/cross-site completion is denied. Privileged admin and tab origin checks are unchanged; no CORS read access is given to null origins.

**Diagnostics:** In Perch MCP → Settings or Activity select **Export complete diagnostics (OAuth + network)**. The JSON contains userscript/gateway version, health, paired/scope counts, bounded local request timing/errors, and a server-side OAuth audit ring (max 100 events over seven days, max 120/minute). Every event contains route class, method, origin category, status, code and trace ID, excluding source, tokens, credentials, private headers, URLs/queries, OAuth request payloads, handles or auth codes. Audit capture is best-effort and cannot block authorization. The old Activity-only export remains separate; zero MCP operations cannot diagnose OAuth setup. A gateway outage still produces a useful partial diagnostic report with failure codes.

Upgrade the **existing** Cloudflare Worker to v0.1.3 (verify `/health.version === "0.1.3"`) and update the Violentmonkey script to matching v0.1.3. Do not reset BOOTSTRAP_SECRET, KV namespace, Registry, Workspaces or pairing. Restart ChatGPT OAuth from the beginning because prior five-minute authorization codes expire. After approval, Continue should navigate back to the OAuth callback. If not, export diagnostics (no need for console screenshots) and correlate the trace IDs without sharing secrets.

## OAuth redirect recovery and PersonaMonkey/LibreWolf qualification (v0.1.4)

**Observed live incident (v0.1.3):** The user approved in Perch MCP; Cloudflare logged `authorize_complete POST 302 COMPLETE`, then a repeat `POST 200 PENDING_OR_INFO`, with no observed `/token` exchange. The first event proves only that the Worker issued a redirect, not that ChatGPT received it. Intermittent local GET/POST failures were independently observed in LibreWolf, improving when PersonaMonkey was disabled. Do not claim a PersonaMonkey bug without tracing its active route policy and proxy.

**Root cause:** Registry `/internal/oauth/consume` irrevocably marked the approval consumed *before* the SDK created the OAuth authorization code and browser navigation completed. A lost 302 then made the original handle unrecoverable. The v0.1.4 gateway persists the exact SDK-generated callback behind the original random handle; a repeat form POST cannot generate another code/Grant. Instead it displays a link labeled **Continue to ChatGPT**. The link uses `rel=noreferrer` and `referrerpolicy=no-referrer`. Existing approvals issued by v0.1.3 cannot be retroactively recovered. If the callback was already redeemed, the client may reject a replay because the OAuth code is one-use; restart authorization then.

**How to retry:** Deploy current `main` to the *existing* Cloudflare Worker and check `/health.version=0.1.4`. Update the existing Violentmonkey script to v0.1.4; keep the existing pairing, Workspace, KV and Durable Objects. Initiate a fresh ChatGPT connector authorization (old codes expire). Approve the exact Client and code in Perch MCP → Agents. Click Continue. The gateway sends a standard HTTP 302 with the client callback. If the browser does not reach ChatGPT, return to the original authorization page and click Continue again: the same handle now shows a manual **Continue to ChatGPT** link without minting new credentials. If PersonaMonkey routes the gateway or `chatgpt.com` to Block/unreachable SOCKS, explicitly configure its permitted route/working proxy for the designated Persona; the gateway cannot override an extension's fail-closed routing. Do not globally disable privacy or store credentials outside the isolated script.

**Observability:** Export Settings → **Export complete diagnostics (OAuth + network)**. `oauthAudit` records `CALLBACK_REDIRECT_ISSUED`, `CALLBACK_RECOVERY_AVAILABLE` and `TOKEN_EXCHANGE_SUCCEEDED` as distinct events. `oauthHandoff` tells whether a token exchange was observed after the last gateway-issued redirect but explicitly notes that events cannot be correlated without storing sensitive OAuth identifiers. Do not equate 302 with end-to-end success. Codes, callback URLs, handles, query strings and credentials are excluded from logs and diagnostic exports. Grant and callback replay state expire according to the original five-minute authorization deadline.

**Failure/recovery table:** `pending` → keep retryable form; `approved` → allocate one Grant and issue SDK code; `processing` → retry status only; `completed` → show exact sealed callback link on repeat; `failed` → revoke provisional Grant and start a new ChatGPT authorization; `revoked` → no callback link; `expired` → start a new authorization. A blocked client navigation is a user/client routing issue, not grounds for a second OAuth code.

## Browser liveness and Grant revocation correction — userscript v0.1.5

**Production fault:** The Cloudflare Workspace Durable Object holds idle `POST /api/v1/tab/poll` for up to 25 seconds. The userscript `GatewayTransport` inadvertently set `AbortSignal.timeout(15000)` whenever a request did not supply an explicit AbortSignal—even though the calculated POST deadline was 30 seconds. Every idle poll therefore timed out at 15 seconds and the browser controller permanently transitioned to offline. A transient failing 60-second heartbeat also stopped the controller while the 180-second lease could remain valid. This was observable as MCP `TAB_OFFLINE` despite an Active remote Workspace. The browser bootstrap additionally did not reconnect an existing Workspace after a new userscript initialization.

**Correction:** The transport now honors the chosen deadline in both signal branches. Controller long polls explicitly permit 45 seconds for the 25-second server hold; transient poll failures retry at most twice on the current lease with bounded backoff. The Worker serializes operations, so re-polling the same lease never creates a second claim or repeats a dispatched effect. Heartbeat network glitches retain valid leases; explicit stale/revoked epochs fail closed. `Pause` aborts the poll promptly. The manager displays `connecting/degraded/connected/offline/blocked` independently from the Registry Workspace state and exports redacted current lease presence, lifetime and poll failure code.

**Reload handling:** On startup and BFCache restore, the isolated content script probes the native editor for at most 20 seconds, reads the bound Workspaces and attempts one new claim only if exactly one active Workspace matches the canonical Generator ID, Draft ID, slug and browserInstallationId. Missing, partial, paused or ambiguous bindings fail closed and require explicit Reconnect. A held lease or unresolved effect remains held; no forced takeover, new binding, Grant revocation or source mutation occurs. The deliberate operator Stop action stores a scoped no-autoresume marker, cleared only after an explicit Reconnect.

**Grant revocation:** `Revoke Grant` now offers a visible inline confirmation, makes exactly one versioned POST, and uses authoritative GET readback to verify revocation even when the POST response is lost. Revoked Grants show a terminal label and no Revoke button. If the outcome remains uncertain, the confirmation becomes a reconciliation instruction and does not offer a blind replay. Revocation does not undo effects already dispatched.

**Deployment:** This is a **userscript-only v0.1.5** correction. Existing Cloudflare gateway `/health.version = 0.1.4` is expected and compatible (schema v1); do not redeploy Cloudflare, delete KV/DO, rotate secrets, recreate Workspaces or re-authorize the connector. Replace the existing Violentmonkey script with the checked `perch-mcp.user.txt`, reload the native editor, verify the local status turns `connected`, then call `workspace_status` from ChatGPT. If PersonaMonkey is enabled, its fail-closed outbound routing must allow an operational path to the gateway; the userscript cannot bypass a blocked or unreachable proxy.

## Native preview activation and tool-contract repair — userscript v0.1.6

**Live operator observation:** Userscript v0.1.5 + gateway v0.1.4 successfully authenticated ChatGPT MCP and executed browser source reads and native identity checks, but `page_eval` returned `UNSUPPORTED_INTERFACE`; `preview_diagnostics` reported console/syntax capture unavailable and unknown freshness. The live redacted export `perch-mcp-diagnostics2.json` (user-provided) records a connected browser with 139541ms of lease remaining, zero poll failures, positive tab poll/heartbeat acknowledgements and a confirmed OAuth token exchange. The browser bridge, OAuth and routing should not be reconfigured to resolve preview failure.

**Root cause:** `RuntimeTools.preview` constructs a native fixed-message `NativeProtocolPreviewBridge` but initializes `PreviewAdapter` with `verified: {}`, forcing `page_eval` and `page_refresh` to return `UNSUPPORTED_INTERFACE` without ever exercising native protocol capability. v0.1.6 now performs an explicit, inert `evaluateJs` constant handshake against the exact preview origin and WindowProxy, verifies request correlation and a valid reply, then permits evaluation. Preview refresh proceeds only after native structural/readiness checks, preserving the existing exact panel/src manifest and render-generation attestation and preamble ownership rules. Missing or changed native capabilities fail closed, never falling back to privileged unsafeWindow eval or frame-script injection. The first read-only preview diagnostic may still report unavailable console capture until a verified native refresh installs its bounded console/error preamble. Syntax errors have no independently verified native collector and remain explicitly unavailable; zero errors is not proof of a clean preview.

**Contract fixes:** `list_files` returns the old `paths` field **and** `entries` with stable path, byte-accurate size and positive UTF-8 `text`/non-text `binary`/zero-byte `empty` classification. `generator_info` now returns known/unknown ownership, native Save predicate and explicit listing value, using only recognized native metadata. No inferred ownership, Save permission or listing from code-edit availability. The original Workspace status fields remain available for compatibility.

**Diagnostics:** The independent redacted Settings export includes a bounded 50-event preview tool ledger (time, tool, duration, success/failure and code), with allowlisted tool names and result codes; it never exports preview JS, source, console text, keys, credentials, OAuth codes or request bodies. `preview_diagnostics` distinguishes captured and missing evidence, including unverified preview freshness. Read-only diagnostics remain accessible when native mutation guards prevent editing. Inspect `preview.events` after a failed call; a failed native handshake records `TIMEOUT`, `BINDING_MISMATCH` or `UNSUPPORTED_INTERFACE` without exposing source.

**Deployment:** Replace existing Violentmonkey userscript with v0.1.6. Cloudflare gateway v0.1.4 and its SQLite/KV records remain unchanged. Do not reset pairing or bind again; retain existing ChatGPT OAuth. Re-open `aleph-alpha#edit`, confirm connected, then first call `preview_diagnostics`, then `page_eval` with `return ({title: document.title, value: 6 * 7});`; inspect `operation_status` terminal result and new diagnostics. Native preview tests are synthetic until run against the user's actual LibreWolf editor; the implementation does not justify enabling production Save/lifecycle gates or claiming screenshot parity.
